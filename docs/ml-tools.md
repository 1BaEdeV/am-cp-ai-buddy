# Операции Go-бэкенда для ML

Подключён внутренний HTTP-интерфейс четырёх инструментов. Промпт, выбор
инструментов и обработка разговора остаются в ML-модуле. Спецификация HTTP
добавлена в `docs/openapi.yaml`.

## Настройка и контекст

Установи одинаковый секрет `ML_TOOLS_TOKEN` в окружении Go API и ML-сервера,
затем перезапусти API. Токен можно создать командой `openssl rand -hex 32`.
При пустом токене внутренние маршруты не регистрируются и возвращают 404.
Секрет хранится на сервере и не передаётся браузеру или LLM.

Каждый вызов инструмента требует заголовков:

- `Authorization: Bearer <ML_TOOLS_TOKEN>` — аутентификация вызывающего сервера;
- `X-Demo-Employee-Id` — ID текущего сотрудника из серверного контекста чата;
- `Content-Type: application/json` — формат аргументов.

ML-сервер сам устанавливает ID сотрудника. Он не берёт его из аргументов
инструмента, сгенерированных моделью. Текущий демо-вход использует вымышленные
ID; Go-сервис заново проверяет роль, профиль и принадлежность ресурса или заявки.

`GET /api/v1/internal/ml/tools` с Bearer-токеном возвращает массив
`{name, description, inputSchema}`. ID сотрудника для списка схем не нужен.
`inputSchema` — JSON Schema аргументов с `additionalProperties: false`.

Вызов: `POST /api/v1/internal/ml/tools/{toolName}`. Тело — непосредственно
JSON-объект аргументов, без обёртки `arguments`. Успешный ответ — 200 с
результатом операции, без дополнительной обёртки.

| toolName | Аргументы | Результат |
| --- | --- | --- |
| `get_role_tools` | `{}` | `resources` и `progress`, как в карточке рабочих доступов |
| `check_tool_access` | `{"resourceId":"gitlab-search-api"}` | `resourceId`, `requiredAccessLevel`, `granted`, `accessLevel`, `sufficient` |
| `prepare_access_request` | `{"resourceId":"gitlab-search-api"}` | `status` и, в зависимости от него, `draft` или `request` |
| `get_access_request_status` | `{"requestId":"..."}` | Полная доступная сотруднику заявка с текущим `status` и результатом выдачи |

`get_role_tools` показывает сохранённый прогресс. `check_tool_access` обращается
к провайдеру и читает фактические права только на обязательный ресурс текущего
стажёра. `granted=true` означает наличие каких-либо прав; `sufficient=true` —
подтверждённый провайдером достаточный уровень. Проверка не выдаёт права,
не создаёт заявку и не изменяет сохранённый `EmployeeAccess`.

## Подготовка и подтверждение

Подготовка возвращает один из трёх результатов:

- `status=draft`, `draft` — черновик одного ресурса с `id`, `resourceId`,
  `approverId`, `parameters`, `createdAt`, `expiresAt`;
- `status=already_granted` — достаточный сохранённый доступ уже есть;
- `status=request_exists`, `request` — активная заявка уже существует.

Уровень, назначение и согласующего определяет backend. Их нельзя передать
в аргументах инструмента. Подготовка не создаёт заявку руководителю.

Покажи сотруднику `draft.parameters` и привяжи карточку к `draft.id`.
После явного подтверждения пользователя интерфейс вызывает существующий
`POST /api/v1/access-requests/drafts/{draftId}/confirm` с `{"confirmed":true}`
и его демо-ID. Этот маршрут не включён в инструменты LLM. Черновик действует
15 минут; повтор подтверждения возвращает уже созданную заявку.

Подготовка доступна только через внутренний инструмент; публичного маршрута
создания черновика нет. Решение руководителя и выдача прав также не являются
инструментами агента.

## Ошибки

Формат: `{"code":"...","message":"..."}`. Исходные ошибки БД в ответ не попадают.

| HTTP | code | Значение |
| --- | --- | --- |
| 400 | `invalid_input` | Неверные или лишние аргументы, пустой ID, неверный JSON |
| 401 | `ml_service_unauthorized` | Неверный или отсутствующий Bearer-токен |
| 401 | `demo_identity_required` | Нет контекста сотрудника или сотрудник неизвестен |
| 403 | `forbidden`, `profile_required` | Неподходящая роль или незаполненный профиль |
| 404 | `resource_not_required` | Ресурс не предусмотрен для сотрудника |
| 404 | `request_not_found` | Заявка отсутствует или недоступна сотруднику |
| 404 | `tool_not_found` | Такого инструмента нет |
| 409 | `resource_changed`, `requirements_not_configured` | Параметры ресурса или правила требуют обновления |
| 413 / 415 | `request_too_large`, `unsupported_media_type` | Тело больше 1 МиБ или Content-Type отличается от application/json |
| 503 | `access_check_unavailable` | Сбой провайдера или тайм-аут проверки |
| 500 | `internal_error` | Неожиданная ошибка исполнения |

## Ручная проверка

После [загрузки демо](demo-data.md), с экспортированным сервисным токеном:

```sh
curl -sS http://localhost:8080/api/v1/internal/ml/tools/get_role_tools \
  -H "Authorization: Bearer $ML_TOOLS_TOKEN" \
  -H 'X-Demo-Employee-Id: intern-alina' \
  -H 'Content-Type: application/json' \
  -d '{}'
```

Ожидаемый исходный прогресс — `completed=2`, `total=4`. Для остальных операций
используй имя и аргументы из таблицы. Сквозной тест
`go test -race ./tests/integration/mltools` вызывает все четыре инструмента,
подтверждает заявки через пользовательский API и ждёт настоящую фоновую выдачу
до 4/4. Он также проверяет чужие заявки, подмену аргументов и отключённые маршруты.

При заданной `ACCESS_TEST_DATABASE_URL` тот же путь проверяется на PostgreSQL.
Отдельный тест имитирует потерю ответа после фактической выдачи: заявка получает
`failed`, а повтор руководителя подтверждает уже выданные права без второй
операции провайдера. [Запуск PostgreSQL-тестов](../backend/tests/integration/README.md).
