# Черновик и заявка на один доступ

Создать запрос на доступ можно только через AI-buddy. Агент вызывает
`prepare_access_request` с ID одного ресурса. Сотрудника backend определяет
из контекста текущего пользователя, а уровень и согласующего — из правил
команды и должности. Модель не выбирает произвольные права и согласующего.

## Данные

`AccessDraft` хранит владельца, команду и должность на момент подготовки,
один ресурс, согласующего, срок действия и копию параметров, показанных
сотруднику. Черновик ещё не является заявкой руководителю.

`AccessRequest` появляется после явного подтверждения владельцем черновика.
Она ссылается на черновик через уникальный `DraftID` и получает номер от
PostgreSQL. Параметры и ссылки копируются из черновика без изменений. В заявке
хранятся статус, время решения руководителя, причина отказа и результат выдачи.
Копия параметров не меняется при последующем редактировании справочников.

`AccessRequestParameters` — общие поля копии параметров, встроенные в обе
таблицы: название ресурса, сервис и внешний ID, уровень, назначение доступа
и имя согласующего. Это не третья таблица. Ссылки `Employee`, `Resource`
и `Approver` загружают актуальные справочники; показанные при подтверждении
значения нужно читать из `Parameters`.

`AccessIssuanceJob` — отдельная таблица очереди выдачи. Задание сохраняется
вместе с одобрением и ссылается на заявку. Хранит количество попыток, время
доступности, срок аренды обработчиком и уникальный токен этой аренды.
После остановки процесса другой обработчик сможет продолжить задание,
а старый токен уже не позволит записать результат поверх новой попытки.

Таблицы позиций черновика, пропущенных ресурсов и результатов по отдельным
ресурсам не нужны: каждый черновик относится ровно к одному доступу.
Если доступ уже есть или заявка существует, операция подготовки возвращает
причину и сведения о существующей заявке, не создавая черновик.

## Последовательность действий

1. Инструмент агента проверяет обязательность ресурса, достаточность текущего
   доступа и отсутствие активной заявки. Сохраняет черновик и показывает его
   сотруднику. Подготовка не отправляет заявку руководителю.
2. Сотрудник явно подтверждает конкретный черновик. Способ подтверждения
   (сообщение в чате или кнопка в сообщении) можно выбрать отдельно; согласие
   должно быть привязано к владельцу и ID черновика. Сам вызов инструмента
   моделью не является согласием сотрудника.
3. Backend в транзакции сначала блокирует сотрудника, затем его черновик.
   Если заявка
   по `DraftID` уже существует, возвращает её даже после истечения срока
   черновика. Иначе проверяет срок, текущие правила, доступ и активные заявки.
   Если параметры изменились, возвращает `ErrDraftChanged`: инструмент должен
   подготовить новый черновик для нового подтверждения.
4. Backend копирует параметры в одну заявку `pending` и устанавливает
   `ConfirmedAt` у черновика в той же транзакции. При конфликте уникальности
   активной заявки транзакция откатывается; существующую заявку нужно прочитать
   после отката. Подмена параметров при подтверждении недопустима.
5. Назначенный руководитель принимает решение только из `pending`.
   Одобрение переводит заявку в `issuing`, отказ с причиной — в `rejected`.
   Изменение состояния выполняется условно по старому статусу; при одобрении
   задание на выдачу сохраняется в той же транзакции.
6. После подтверждённой выдачи обработчик сохраняет `EmployeeAccess`,
   `GrantedAt` и статус `granted` в одной транзакции. При ошибке сохраняет
   `failed` и `LastError`. Перед повтором или после тайм-аута сначала проверяет,
   не выполнил ли провайдер предыдущую операцию. ID заявки подходит для
   постоянного ключа операции выдачи.

## Ограничения и границы моделей

- В черновике и заявке один обязательный `ResourceID`; коллекций ресурсов нет.
- Уникальный `DraftID` в заявке не позволяет создать две заявки из одного
  черновика. Отдельная таблица результатов подтверждения для этого не нужна.
- Частичный уникальный индекс разрешает только одну активную заявку
  сотрудника на ресурс. Активными считаются `pending`, `issuing` и `failed`.
  Ошибка не освобождает ресурс для второй заявки: продолжается обработка
  существующей. После `rejected` можно подготовить новый черновик;
  после `granted` новый запрос зависит от проверки фактического доступа.
- База проверяет допустимость статуса, наличие причины отказа, срок черновика,
  уникальность номера и внешние ключи. Номера назначаются PostgreSQL автоматически,
  но не обязаны идти без пропусков.
- Проверки владельца, роли руководителя, неизменности параметров и переходов
  состояний выполняет сервис `internal/accessrequest`. Факт явного согласия должен
  проверить вызывающий обработчик чата или кнопки перед подтверждением.
- Правило «создание только через агента» реализуется доступностью серверного
  инструмента подготовки. Отдельного публичного обработчика для произвольного
  создания заявки быть не должно. Подтверждение может обрабатываться кнопкой
  внутри чата, если выбран такой интерфейс.

## Операции бизнес-слоя

Сервис заявок находится в `backend/internal/accessrequest` и создаётся через
`accessrequest.NewService(db)`. Он использует общее подключение GORM, как
существующие сервисы авторизации и карточки ресурсов. Карточка и прогресс
остаются в `internal/access`; общие проверки требований и уровней прав
используются обоими пакетами.

| Метод | Поведение |
| --- | --- |
| `PrepareAccessRequest(ctx, employeeID, resourceID)` | Проверяет профиль, правила, сохранённый доступ и активные заявки. Возвращает черновик, `already_granted` или `request_exists`. |
| `ConfirmAccessRequest(ctx, employeeID, draftID)` | Повторно проверяет условия и создаёт одну заявку. Возвращает заявку и `created`; при повторе `created=false`. |
| `GetAccessRequest(ctx, employeeID, requestID)` | Читает свою заявку для стажёра или назначенную заявку для руководителя. Подходит для инструмента чтения статуса. |
| `ListAccessRequests(ctx, employeeID, filter)` | Стажёру возвращает свои заявки с фильтрами; руководителю — очередь назначенных ему заявок `pending` без фильтров. |
| `DecideAccessRequest(ctx, approverID, requestID, input)` | Принимает `approve` или `reject`. Повтор того же решения с той же причиной возвращает прежний результат. Противоположное решение даёт `ErrRequestAlreadyDecided`. |
| `RetryAccessIssuance(ctx, approverID, requestID)` | Назначенный руководитель возвращает заявку `failed` в выдачу. Новая заявка не создаётся. |
| `ProcessNextIssuance(ctx, provider)` | Обрабатывает одно готовое задание. Возвращает `false`, если очередь пуста или задания заняты. |

Черновик действует 15 минут (`DraftTTL`). Подтверждение не принимает уровень,
согласующего или назначение из запроса: значения копируются из сохранённого
черновика. Чужой черновик возвращает `ErrDraftNotFound`, чужая заявка —
`ErrRequestNotFound`, чтобы не раскрывать существование чужих данных.

Фильтр списка стажёра: `Group` принимает `all`, `active`, `completed`; также доступны
`Status`, `ResourceID`, `Limit` (по умолчанию 20, максимум 100) и `Offset`.
`Total` относится к отфильтрованному списку; `Counts` — ко всем заявкам,
которые разрешено видеть пользователю. В `active` входят `pending`, `issuing`
и `failed`, в `completed` — `granted` и `rejected`.

Список руководителя всегда содержит только назначенные ему заявки `pending`.
Учитываются только `Limit` и `Offset`; остальные поля фильтра игнорируются.
Счётчики относятся к этой очереди: `Total`, `Active` и `Pending` равны её размеру,
остальные равны нулю. После решения заявка исчезает из очереди. При этом
`GetAccessRequest` позволяет руководителю читать назначенную ему заявку
в любом статусе, а `RetryAccessIssuance` — повторить выдачу при ошибке.

Карточка ресурсов теперь учитывает активные заявки и возвращает краткие
сведения о заявке. `Progress.InProgress` считает ресурсы на согласовании
и выдаче, `Progress.Failed` — ошибки. `Completed` увеличивается только по
подтверждённому `EmployeeAccess`.

## Подключение выдачи и чата

`AccessProvider` определяет операции проверки фактических прав и выдачи.
Адаптер обязан соблюдать контекст и идемпотентность по ID заявки, который
передаётся как постоянный `operationID` на всех попытках. Обработчик сначала
проверяет доступ, при необходимости выдаёт его, затем проверяет результат.
Успешный ответ на команду выдачи сам по себе не означает `granted`.

Сетевые операции ограничены 30 секундами и выполняются вне транзакции БД.
Задание арендуется на минуту. Сбой процесса оставляет заявку в `issuing`;
после истечения аренды следующая попытка сначала проверит прежний результат.
Ошибка провайдера сохраняет `failed` и понятное сообщение без исходных
служебных данных. Явный повтор запускает назначенный руководитель.
Если внешний доступ выдан, а запись в БД не удалась, задание тоже можно
восстановить по аренде: повтор обнаружит выданные права.

Перед сетевыми операциями и перед записью подтверждённого доступа сервис
сверяет сервис и внешний ID ресурса с согласованными параметрами.
Если тот же `ResourceID` переназначен другому внешнему ресурсу, заявка
переходит в `failed`, а доступ не засчитывается новому ресурсу.
Руководителю нужно проверить настройки; после восстановления исходного
назначения можно повторить обработку прежней заявки. Переименование
ресурса не препятствует выдаче и не меняет сохранённый снимок.

Реализованы сервисный слой, один шаг фонового обработчика, HTTP-обработчики
действий пользователя и [демо-провайдер выдачи](demo-provider.md) с постоянным
состоянием и воспроизводимыми сбоями. Запуск фонового цикла и регистрация
инструментов агента пока не подключены.
Подтверждение нельзя предоставлять LLM как самостоятельное действие без
проверки согласия.

## HTTP API

Обработчики находятся в `backend/internal/handler/accessrequest` и подключены
в `cmd/api/main.go`. Во всех запросах нужен `X-Demo-Employee-Id`. Пользователь
берётся только из заголовка; подменить владельца или согласующего через JSON
или параметры списка нельзя. Роль и доступ к конкретной записи проверяет сервис.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/access-requests/drafts/{draftId}/confirm` | Явное подтверждение сотрудника в интерфейсе чата. Тело: `{"confirmed":true}`. Возвращает одну заявку: `201` при создании, `200` при повторе. При создании `Location` указывает на карточку. |
| `GET /api/v1/access-requests` | Свои заявки стажёра или очередь `pending` руководителя. Возвращает `items`, `total`, `counts`, `limit`, `offset`. |
| `GET /api/v1/access-requests/{requestId}` | Карточка заявки в любом статусе в пределах прав пользователя. |
| `POST /api/v1/access-requests/{requestId}/decision` | Решение назначенного руководителя. Тело: `{"decision":"approve"}` или `{"decision":"reject","reason":"Причина"}`. |
| `POST /api/v1/access-requests/{requestId}/retry` | Повтор выдачи по прежней заявке назначенным руководителем. Тело не требуется. |

Публичного `POST /access-requests` и HTTP-подготовки черновика нет.
`prepare_access_request` должен вызывать `PrepareAccessRequest` на сервере
в доверенном контексте текущего сотрудника. Подтверждение предназначено
для действия пользователя после показа черновика, а не для автономного вызова LLM.

JSON-запросы требуют `Content-Type: application/json`, неизвестные поля
отклоняются. Для подтверждения требуется именно `confirmed=true`: без него
возвращается `400 confirmation_required`. Подтверждение не принимает
`resourceId`, `accessLevel`, `employeeId` или `approverId`.
Причина отказа после удаления пробелов обязательна и ограничена 2000 символами.
Тело JSON ограничено 1 МиБ (`413`), неверный тип содержимого даёт `415`.

Для списка допускаются только `group`, `status`, `resourceId`, `limit`, `offset`,
каждый не более одного раза. Неверный формат пагинации, неизвестные или
повторные параметры дают `400 invalid_input`. Значения group и status
проверяет сервис с учётом роли; руководителю они не меняют очередь pending.

Ошибки возвращаются как `{"code":"...","message":"..."}`.
Неизвестный сотрудник даёт `401`, запрещённая роль — `403`, чужой или
отсутствующий черновик/заявка — `404`. Истёкший/изменённый черновик,
существующий доступ или активная заявка, конфликт решения и неподходящий
статус операции дают `409` с отдельным кодом причины. Неожиданные ошибки
дают `500 internal_error` без служебных подробностей. JSON-ответы запрещают
кеширование. Контракт описан в `docs/openapi.yaml` для одного доступа.

## Проверки

Unit-тесты бизнес-слоя находятся в `backend/internal/access` и
`backend/internal/accessrequest`. Запуск из `backend`:
`go test ./internal/access ./internal/accessrequest -cover`.
Ответы SQL подставляются через `go-sqlmock`, время фиксировано, внешний
провайдер заменён тестовым. Проверяются успешные операции, повторы,
изменившиеся условия черновика, видимость заявок, ошибки хранения,
отмена контекста и потеря аренды задания. Этот запуск не включает
интеграционные тесты и не требует работающей БД.

Интеграционные тесты заявок находятся в
`backend/tests/integration/accessrequest` и разделены на подготовку черновика,
подтверждение, решения, чтение, выдачу и PostgreSQL. Проверки с SQLite и
тестовым провайдером запускаются через `go test ./tests/integration/accessrequest`
из `backend`. Истечение срока черновика и аренды моделируется изменением
тестовых записей в БД; обработчики запускаются публичными методами сервиса.

Тесты HTTP-слоя проверяют маршруты, JSON, пагинацию, ошибки и отсутствие
подмены контекста. Интеграционный тест HTTP + сервис + SQLite проходит
подготовку через серверный сервис, подтверждение, решение, ошибку выдачи,
повтор и успешную выдачу через тестовый провайдер. Он находится в
`backend/tests/integration/http/accessrequest` и запускается через
`go test ./tests/integration/http/...`. Unit-тесты хэндлеров с подставным
сервисом остаются в `internal/handler/accessrequest`.

Для проверок настоящих блокировок PostgreSQL задай `ACCESS_TEST_DATABASE_URL`
и запусти `go test ./tests/integration/accessrequest -run Postgres -v` из `backend`.
Тесты создают отдельную случайную схему и удаляют её после выполнения;
пользователю базы нужно разрешение `CREATE SCHEMA`. Без этой переменной
PostgreSQL-тесты пропускаются. Они проверяют параллельные подтверждения,
противоположные решения руководителя, захват задания двумя обработчиками
и назначение номера заявки базой.
