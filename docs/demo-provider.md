# Демо-провайдер доступов

`backend/internal/demoprovider` реализует интерфейс `accessrequest.AccessProvider`.
Это имитация внешних систем в том же Go-приложении. Состояние хранится в PostgreSQL
и сохраняется при пересоздании провайдера или перезапуске приложения.

Поддерживаются ресурсы из справочника `Resource`: сервис и внешний ID должны
совпадать, уровень должен входить в `AccessLevels`, сотрудник должен существовать.
Это покрывает вики, YouTrack, GitLab, Grafana и остальные сервисы из демо-данных.
Проверки согласования и принадлежности ресурса команде выполняет бизнес-сервис.

## Использование

```go
provider := demoprovider.NewProvider(db)
requests := accessrequest.NewService(db)

// Один шаг уже существующего обработчика; при пустой очереди processed=false.
processed, err := requests.ProcessNextIssuance(ctx, provider)
```

`CheckAccess(ctx, target)` возвращает фактически выданный уровень. Если прав нет,
возвращает `Granted=false` без ошибки. Проверка не создаёт права или записи состояния.
Достаточность уровня проверяет бизнес-сервис; наличие меньшего уровня тоже означает
`Granted=true`, но не позволяет завершить заявку на более высокий уровень.

`GrantAccess(ctx, operationID, target)` сохраняет права и успешную операцию в одной
транзакции. Постоянным `operationID` служит ID заявки. Повтор с теми же параметрами
возвращает успех без новой выдачи, даже если после неё включён демо-сбой. Повтор
того же ID с другим сотрудником, сервисом, ресурсом или уровнем возвращает
`ErrOperationConflict`. Неудачная транзакция не сохраняет успешную операцию:
после устранения ошибки её можно повторить с прежним ID.

Строка прав блокируется на время изменения. Одновременные выдачи сериализуются;
более высокий уровень GitLab, Figma или S3 не понижается запросом меньшего уровня.

## Начальные права и сбои

`SeedAccess(ctx, target)` задаёт начальные права без заявки и не понижает уже
выданный уровень. Вызывается служебным кодом подготовки демо, не инструментом LLM.
Начальные права нужно согласовать с `EmployeeAccess` из демо-данных.

`SetFailure(ctx, target, mode)` сохраняет режим для сотрудника и внешнего ресурса,
не меняя существующие права. Допустимые режимы:

| Режим | Поведение |
| --- | --- |
| `FailureNone` | Отключает сбой. |
| `FailureCheck` | `CheckAccess` возвращает `ErrCheckFailed`. |
| `FailureGrant` | Новая выдача возвращает `ErrGrantFailed`; транзакция откатывается. |
| `FailureAfterGrant` | Права и операция сохраняются, но первый ответ — `context.DeadlineExceeded`. |

Последний режим имитирует потерю ответа после успешной выдачи без реального
ожидания тайм-аута. Следующая проверка обнаружит права, а повтор той же операции
вернёт успех. Режимы сохраняются в БД и переживают пересоздание провайдера.
Служебные методы не опубликованы как пользовательские HTTP-маршруты.

## Данные и подключение

- `DemoProviderAccess` хранит права и режим сбоя по сотруднику, сервису и внешнему ID.
- `DemoProviderOperation` хранит ID и параметры успешно выполненной операции.
- Таблицы подключены к `AutoMigrate` в `cmd/api/main.go`.

Провайдер не изменяет `EmployeeAccess`, заявки и задания. После подтверждённой
выдачи это делает `ProcessNextIssuance`. Фоновый цикл и регистрация инструментов
агента остаются отдельными задачами; автоматической загрузки демо-данных пока нет.

## Тесты

Из папки `backend`:

```sh
go test ./internal/demoprovider -cover
go test -race ./internal/demoprovider ./tests/integration/demoprovider
```

Unit-тесты используют SQL-мок. Интеграционные проверки используют временную SQLite
и настоящий демо-провайдер, включая выдачу через сервис заявок и прогресс 2/4 → 3/4 → 4/4.
Проверяется откат операции при ошибке записи прав и восстановление после потерянного ответа.

Конкурирующие выдачи и конфликт ID проверяются отдельно на PostgreSQL:
`go test ./tests/integration/demoprovider -run Postgres -v` с заданной переменной
`ACCESS_TEST_DATABASE_URL`. Тест создаёт собственную случайную схему; без переменной
пропускается. Пользователю тестовой базы требуется право `CREATE SCHEMA`.
