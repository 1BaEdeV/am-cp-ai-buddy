# AI-buddy — frontend

React + TypeScript + Vite. Интерфейс повторяет предоставленный HTML-макет:
единый план из трёх шагов, боковая сводка, задания и чат, профиль, заявки
стажёра и очередь руководителя. Шрифты и иллюстрация локальные, внешние CDN
для оформления не нужны. Источники перечислены в [THIRD_PARTY.md](THIRD_PARTY.md).

## Запуск

Нужен Node.js 24 или новее. Из папки `frontend`:

```sh
npm ci
npm run dev
```

Открыть [localhost:5173](http://127.0.0.1:5173/). По умолчанию включён
самостоятельный демо-просмотр, PostgreSQL и Go для него не требуются.

## Демо-просмотр

На экране входа есть стажёр Алина и руководитель Дмитрий. Новый сотрудник
Иван проходит регистрацию. После входа переключатель роли позволяет быстро
показать обе стороны согласования.

Сценарий:

1. Войти стажёром, открыть знакомство и отметить его после общения.
2. Открыть рабочие доступы: начальное состояние — 2 из 4.
3. В чате выбрать GitLab. Помощник покажет черновик одного ресурса.
4. Проверить параметры и нажать «Подтвердить отправку».
5. Переключиться на руководителя, открыть заявку и одобрить её.
6. После имитации выдачи прогресс станет 3/4. Повторить для Grafana — 4/4.
7. В плане завершены два этапа; первая задача показывает «Скоро».

Отказ требует причины. Руководитель видит только назначенные ему `pending`,
стажёр — свои заявки с фильтрами. `failed` относится к активным заявкам.
Повтор подтверждения возвращает прежнюю заявку. У нового сотрудника свои
ресурсы и отдельная переписка для каждого задания.

Демо использует подготовленные ответы, а не LLM. Его данные сохраняются
в `localStorage` под ключом `ai-buddy-demo-v1`. Для нового показа можно удалить
этот ключ через инструменты браузера. ID вошедшего сотрудника хранится только
в памяти: обновление страницы снова показывает вход, прогресс сохраняется.

## Подключение Go API

Запусти backend с миграциями и демо-данными по инструкции в корневом README.
Затем в `frontend`:

```sh
cp .env.example .env.local
```

В `.env.local` установи:

```dotenv
VITE_DATA_SOURCE=api
API_PROXY_TARGET=http://127.0.0.1:8080
VITE_API_BASE_URL=/api/v1
```

Перезапусти Vite. Локальный сервер проксирует `/api` в Go, поэтому браузер
обращается к одному origin. Для production сборка находится в `dist`;
хостинг должен отдавать frontend и проксировать `/api` в Go на том же домене.
`API_PROXY_TARGET` настраивает сервер разработки, а не production-хостинг.

Подключены реальные операции:

| Экран / действие        | Маршрут                                                       |
| ----------------------- | ------------------------------------------------------------- |
| Вход, регистрация       | `POST /auth/login`, `POST /auth/register`                     |
| Рабочие доступы         | `GET /onboarding/tasks/working-accesses`                      |
| Список и карточка       | `GET /access-requests`, `GET /access-requests/{id}`           |
| Подтверждение черновика | `POST /access-requests/drafts/{id}/confirm`, `confirmed=true` |
| Решение руководителя    | `POST /access-requests/{id}/decision`                         |
| Повтор после ошибки     | `POST /access-requests/{id}/retry`                            |

Префикс таблицы — `/api/v1`. Сотрудник передаётся в `X-Demo-Employee-Id`.
Параметры заявки берутся из черновика. Прямого создания черновика браузером нет.
Статусы и счётчики периодически обновляются, включая результат фоновой выдачи.

Общий план, знакомство и чат используют контракты `docs/openapi.yaml`.
Пока соответствующих хэндлеров нет, интерфейс показывает недоступность раздела;
настоящие данные не заменяются демо-ответами. Карточка доступов и заявки при
этом продолжают работать. Отсутствие общего плана не подтверждает знакомство
и не открывает первую задачу.

Карточка заявки поддерживает ссылку вида `/#requests?request=<id>`.
После входа по такой ссылке руководитель может открыть назначенную заявку
в любом статусе, в том числе `failed`, и повторить выдачу. Права проверяет Go.

## Передача черновика из чата

UI ожидает `TaskChat` с массивом `messages`. Сообщение помощника может содержать
`draft` — результат серверного `prepare_access_request`:

```ts
{ id, role: 'assistant', text, createdAt, draft: { id, resourceId, approverId, parameters, createdAt, expiresAt } }
```

При наличии `draft` frontend показывает копию параметров и кнопку явного
подтверждения. `request` в сообщении позволяет открыть существующую заявку.
Эти структурированные поля нужно передать из будущего серверного хэндлера чата.
Агент не подтверждает заявку за пользователя.

`ML_TOOLS_TOKEN` остаётся в окружении Go и ML-сервера. Не задавай его в
`VITE_*`: эти переменные попадают в браузерную сборку. Frontend не вызывает
`/internal/ml/tools` и не отправляет сервисный Bearer-токен.

## Проверки

```sh
npm run build
npm run lint
npm run format:check
npm test
npm run test:coverage
npx playwright install chromium
npm run test:e2e
```

Unit-тесты проверяют вход и регистрацию, навигацию, план адаптации, чат,
подтверждение и истечение черновика, фильтры и пагинацию заявок, решения
руководителя и повтор выдачи. Также проверяются HTTP-контракт, ошибки,
защита от повторов в демо, разделение пользователей, фоновый опрос
и обработка запоздалых ответов. Playwright проверяет
полный демо-сценарий на компьютере и телефоне, отказ с причиной, регистрацию,
повторный вход, ссылки на заявки и режим API. Скриншоты и трассы ошибок
сохраняются в игнорируемой папке `test-results`.

Команда `npm run test:coverage` измеряет общее покрытие Vitest через V8.
В расчёт входят все исполняемые файлы `src`, включая React-компоненты,
`App.tsx`, точку входа и оба клиента данных. Исключены сами тесты,
их вспомогательные файлы и `types.ts`, содержащий только TypeScript-типы.
Браузерные тесты Playwright в этот процент не входят.

Установлен минимальный порог **81% отдельно для строк, выражений, функций
и ветвлений**. При падении любого показателя ниже порога команда завершается
с ошибкой; та же проверка выполняется в CI. Это позволяет обнаружить
снижение покрытия при добавлении нового кода.

Результат выводится в терминал. Подробный HTML-отчёт — `coverage/index.html`,
цифры для автоматической обработки — `coverage/coverage-summary.json`.
Папка `coverage` не коммитится.

Для отдельного тестового Go API со свежими демо-данными и работающим обработчиком:

```sh
export LIVE_API_URL=http://127.0.0.1:8088
export LIVE_ML_TOOLS_TOKEN='<тот же ML_TOOLS_TOKEN, что у тестового API>'
npm run test:e2e -- --project=live
```

Этот тест создаёт и одобряет две настоящие заявки в тестовой БД, поэтому
используй отдельную PostgreSQL. Сервисный вызов подготовки выполняется только
процессом теста. Подменяется один отсутствующий маршрут чтения чата: он отдаёт
полученный от Go черновик. Вход, подтверждение, решения, статусы, выдача и прогресс
идут через реальные Go API и PostgreSQL. Без этих переменных live-тест пропускается.

## Структура

```text
src/
  App.tsx              # Сессия, навигация, обновление данных и модальные окна
  components/          # Вход, план, задания, чат, заявки и общие элементы
  lib/api.ts           # Клиент Go API и обработка ошибок
  lib/demo.ts          # Изолированный демо-сценарий
  lib/types.ts         # DTO для API и интерфейса
  lib/use-resource.ts  # Загрузка, опрос и защита от устаревших ответов
  styles.css           # Базовые стили HTML-макета
  app.css              # Стили приложения и адаптивная версия
public/                # Manrope, лицензия, логотип и иллюстрация
e2e/                   # Браузерные проверки
```
